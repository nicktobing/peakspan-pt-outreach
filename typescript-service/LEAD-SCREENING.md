# Directory lead screening

The authenticated `POST /api/admin/leads/screen` endpoint accepts `{ "leads": [...] }`, up to 4,000 directory rows / 3.5 MB JSON. Rows use `business_name`, `website_url`, `public_email`, `email_address`, `instagram_url`, and `public_phone`. Other CSV columns are ignored by the endpoint, but the original file should be retained by the operator.

Every request reads the full connected GHL location before returning a result. Any provider, field lookup, or pagination failure produces HTTP 503 and clears no leads. No contact is created, updated, tagged, enrolled, or contacted by this endpoint. It is available while Instagram sending is disabled.

Matching uses case-normalized email, Australian phone normalization, Instagram handles/profile URLs, and website hostname. Instagram URLs in any custom field or website are recognized; plain handles require an Instagram/profile field mapping. Company/full-name-only matches are held for human review. Shared website domains are deliberately conservative: different branches or franchises can be held together. No fuzzy name guesses or mailbox-provider-specific email rewriting is used.

Duplicate identities within the file are grouped transitively before GHL exclusions are decided. If any member matches an existing GHL contact, the whole group is excluded or held, independent of the existing contact's tags. New groups with conflicting Instagram identities are held. Otherwise one row with a valid Instagram profile is selected and the remaining rows are marked duplicate. Missing profiles are held.

`new_needs_qualification` means no match found in the fields returned by GHL at `checkedAt`. It does not mean verified account ownership, verified email, campaign qualification, prior following, or permission to send. Data absent from GHL cannot be matched. `row` is the one-based CSV record position including the header (not a physical line number for multiline fields).

## Live directory like launch

`POST /api/admin/leads/import` accepts one lead, related duplicate-row `variants`, and dated operator qualification evidence: `australianPtBusiness: true`, `officialInstagramLinked: true`, evidence URLs, rationale, and checkedAt (no older than seven days). Both API routes require the admin bearer token. Import requires Production and `DIRECTORY_LAUNCH_ENABLED=true`. GET lists completed import records, or inspects a specific record with `?id=UUID`. Never submit invented qualification evidence.

Imports are serialized per GHL location by persistent database claims. The normalized Instagram identity is permanently reserved. Each acquired import performs a new complete GHL scan before create; duplicate or ambiguous matches are skipped without modification. The create endpoint is used, never upsert. The create phase is saved first, then the returned contact ID is saved before a second full duplicate scan. The original website/email/phone are retained in GHL. Instagram mapping and qualification evidence live in the admission ledger and a GHL note. Only a confirmed new contact receives the dedicated `peakspan-directory-qualified` tag; no prior follow or legacy qualification tags are fabricated. An uncertain create or later reconciliation failure pauses the import and blocks subsequent imports. Repeated requests inspect the existing claim without sending another create. The five-minute Slack monitor covers paused imports and abandoned imports over 15 minutes old.

`IG_BATCH_SOURCE=directory` selects only completed admission records. The ordinary GHL path retains its prior qualified+ig-followed requirements. Directory batches instead require a completed import, the dedicated qualification tag, no stop/completed tags or suppression, and a fresh GHL duplicate check excluding only their own newly created contact before discovery and every send authorization. The source and exact imported identity are persisted in the batch, so a later environment change cannot reinterpret an old batch. Existing GHL contacts cannot be admitted merely by adding the new tag. External concurrent GHL writers cannot share the service lock; the post-create and pre-send scans hold discovered conflicts. GHL identifiers absent from provider data cannot be matched.

Launch uses the existing manual batch-start endpoint and durable Workflow engine: at most ten profiles/actions per session by default, 120-second inter-item delays, and the shared rolling daily action budget. Closing the operator session does not stop a running workflow. This releases only the like stage, not follow/comment/DM sending or an automatic recurring campaign. All steps must use the persisted claim and provider references after interruption. Import and Instagram execution flags are independent.

### Known-contact recovery

GET with `?id=UUID&inspect=1` rechecks the saved contact's presence, creation timestamp and other GHL matches. PATCH with `{ "id": "UUID", "action": "reconcile" }` is a bounded recovery for a paused import with a saved contact ID, after at least 60 seconds. It cannot create a contact or add/retry a note. It rechecks GHL, requires saved proof that the returned contact was new (or a provider creation timestamp within the import window for older records), and idempotently applies only the dedicated qualification tag. Qualification evidence remains in the admission ledger if a CRM note could not be verified. Concurrent recovery is claimed once. Failed records retain their paused step and a sanitized provider failure category, never raw provider text.

Instagram is the required outreach identity; email and phone are optional enrichment. GHL contacts are created with both `name` and `firstName`; if the directory business name is empty, the normalized Instagram handle is used as the CRM display name. This represents Instagram-qualified rows without inventing an email or phone. A paused create with no returned contact ID can use `action: "retry_rejected"` only once, only for a settled, definitive GHL HTTP 400, and only after a fresh complete GHL scan proves there is still no matching contact. The retry reuses the same permanent import claim, records its retry count before sending, and stops again on any uncertain result. A changed retry state receives a new deduplicated Slack alert so the operator guidance reflects whether a contact ID is now saved.
